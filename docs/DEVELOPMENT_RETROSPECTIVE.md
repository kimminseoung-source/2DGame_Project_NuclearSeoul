# 「부산까지」 작업 회고와 학습 기록

이 문서는 개발 중 반복해서 막힌 부분, 사용자가 직접 비교하고 판단한 내용, 다음 작업의 확인 기준을 기록한다. 수업 내용은 질문하고 확인한 범위까지 적고, 혼자 구현할 수 있는지는 직접 해 본 뒤 기록한다.

## 반복해서 생긴 문제

| 문제 | 실제로 있었던 일 | 다음 작업의 확인 기준 |
| --- | --- | --- |
| 실행하는 프로젝트 경로가 다름 | VS Code에서 OneDrive의 예전 `main.py`를 실행해 네모 데모가 나왔다. 현재 Desktop 프로젝트에는 방공호 버전이 있었다. | F5 실행 로그의 프로젝트 경로와 시작 화면을 함께 확인한다. |
| 프레임 수와 자연스러운 동작을 혼동함 | Blender 샘플과 6·8프레임 도트를 비교한 뒤 사용자가 초기 4프레임 도트를 선택했다. 무릎만 눌러 표현한 조용히 걷기도 실제로 살금살금 걷는 느낌이 부족했다. | 장수를 늘리기 전에 체중 이동, 발 교대, 중간 자세를 확인한다. 게임 표시 크기에서 비교한다. |
| 동작·방향을 바꿀 때 캐릭터가 달라 보임 | 별도 시트의 크기와 명암이 달라 서기·걷기·조용히 걷기 또는 직선·대각선 전환에서 차이가 드러났다. 후드 색 차이는 렌더링 픽셀을 읽어 보정 효과를 확인했다. | 같은 위치에서 동작과 방향을 바꾸며 후드·배낭·바지의 명암과 발 기준점을 확인한다. 후드의 측정값과 전체 그림체에 대한 눈 검사를 구분한다. |
| 재생 순서가 맞아도 자세가 틀림 | 좌하향 일반 걷기의 두 디딤 자세가 같은 발을 앞으로 내밀었다. 사용자가 앞발이 중간을 지난 뒤에도 다시 앞으로 나오는 장면을 짚었다. | `2 → 3 → 4 → 3` 순서로 재생해 두 디딤 자세에서 실제로 발이 교대하는지 방향마다 확인한다. |
| 입력을 떼는 순서가 마지막 자세를 바꿈 | 대각선 키 하나를 먼저 떼면 남은 직선 입력이 정지 방향을 바꿨다. 사용자가 대각선 자세를 유지하기 원해 두 키 해제 사이의 허용 간격을 0.2초로 정했다. | 두 키를 동시에 떼는 경우, 한 키씩 떼는 두 순서, 한 키를 계속 눌러 직선으로 전환하는 경우를 확인한다. |

## 함께 확인한 내용

2026-11-07에 대각선으로 완전히 멈춘 뒤 아래 키를 새로 눌러도 0.2초 유예가 적용되는 문제를 발견했다. 마지막으로 바라본 방향과 키 해제가 진행 중인지 여부를 따로 관리해 수정했다. 모든 이동 키를 뗀 뒤 새로 움직이면 첫 업데이트에서 새 방향을 적용한다.

조작감을 논의한 뒤 키 해제 유예를 0.05초로 줄였다. 유예 중에는 이동과 시선을 함께 대각선에 두고, 한 키를 계속 누르면 이동과 시선이 동시에 직선으로 바뀐다. 두 키를 모두 떼면 즉시 멈춘다.

- **수업 코드 구조.** 게임 루프가 입력·갱신·그리기를 맡고, `Player` 같은 객체에 상태와 동작을 묶는 이유를 수업 예제와 프로젝트 코드로 비교했다.
- **스프라이트 시트와 재생 순서.** 한 줄이 한 방향이고 칸마다 다른 자세가 들어간다. 현재 일반 걷기에서 첫 칸은 대기이고, 이동하면 2·3·4·3번 칸을 반복한다. 사용자가 실제 그림을 보고 반대쪽 발이 나와야 하는 시점을 짚었다.
- **제작 방법과 그림체 판단.** Blender에서 3D 동작을 만들어 2D 이미지로 뽑는 과정을 시험했다. 사용자는 같은 동작의 비교 결과를 보고 기존 도트 그림체를 프로젝트 기준으로 선택했다.
- **이동 속도와 자세 전환.** F1에서 이동 속도를 조절할 수 있게 했고, 대각선 속도와 정지 방향을 따로 확인했다. 사용자가 요구한 0.2초는 이동 속도가 아니라 마지막 대각선 방향을 유지하는 입력 간격이다.

## AI가 놓친 부분과 확인 방법

| 실제 사례 | AI가 놓친 부분 | 개발할 때 확인할 것 |
| --- | --- | --- |
| 대각선 걷기에서 같은 발을 두 번 내딛음 | 그림 생성 요청에는 발 교대를 명시했고 코드도 정해진 순서로 재생했지만, 생성된 두 디딤 자세의 앞발이 같았다. | 재생 테스트에 더해 두 자세를 나란히 놓고 무릎 패드와 부츠로 같은 다리를 추적한다. 생성 요청과 실제 결과를 따로 확인한다. |
| Shift 또는 방향 전환에서 명암이 튐 | AI가 제작 가이드를 참조했지만, 같은 위치에서 동작을 전환해 비교하는 검수가 빠졌다. 후드 색을 보정한 뒤에도 시트별 그림자 모양에는 차이가 남았다. | 같은 배경·위치·게임 표시 크기로 전환 전후를 비교한다. 후드의 RGB 측정은 한 부분의 증거로 쓰고, 배낭·바지와 실루엣은 따로 확인한다. |
| 대각선에서 정지한 뒤 직선으로 움직일 때 시선이 늦음 | 처음에는 사용자가 제안한 0.2초를 적용했지만, 완전 정지 후 새 입력과 이동 중 키 하나를 떼는 상황을 충분히 구분하지 않았다. | 입력을 떼는 순서와 이동·시선의 일치를 함께 본다. 사용자가 제안한 값에는 기대하는 조작감을 먼저 묻거나 대안을 제시한다. 현재 0.05초 방식은 코드로 입력 순서를 검증했다. 실제 손으로 느끼는 조작감은 플레이하면서 판단한다. |
| 스프라이트 메모리와 실제 성능 | 이미지 해상도로 메모리 규모를 추정할 수 있지만, 그 수치만으로 FPS나 실제 사용량을 판단할 수 없다. | NPC 수와 맵을 고정해 변경 전후 프레임 시간을 측정하고, 계산한 추정치와 실측을 구분한다. 기준은 [PLAN의 성능 점검](../PLAN.md#개발-중-성능-점검-기준)에 둔다. |

## 다음에 직접 해 볼 작업

- 조용히 걷기 시트 한 방향에서 중간 자세 한 칸을 직접 고치고, 원래 캔버스 크기와 투명 배경으로 저장한 뒤 게임에서 비교한다.
- 프레임 순서가 어색한 경우 그림의 자세가 문제인지, 코드의 재생 순서나 시간 값이 문제인지 먼저 구분한다.

## 기록 방법

개발 중 새 문제가 반복되거나 사용자 피드백으로 기준이 바뀌면 이 파일에 덧붙인다. 한 건에는 **날짜·버전, 보인 현상, 사용자가 확인하거나 결정한 내용, 수정과 검증 결과, 남은 점**을 적는다. 확인되지 않은 원인과 완료 여부는 그대로 표시한다. 아트 규격은 [도트 리소스 제작 가이드](../assets/ART_GUIDE.md), 조작과 실행은 [README](../README.md), 이후 개발 순서는 [PLAN](../PLAN.md)에 기록한다.

변경을 마무리할 때 관련 문서를 같이 업데이트한다. README에는 현재 실행과 조작, PLAN에는 다음 작업과 성능 기준, 아트·애니메이션 가이드에는 적용 중인 리소스 규격, 이 회고에는 실제 시행착오와 배운 점을 둔다. 관련 기록은 서로 링크하고, 같은 내용을 여러 곳에 복사할 경우 기준이 되는 문서 한 곳을 정한다.

기록이 길어져 현재 상태를 찾기 어려워지면 요약 Markdown을 만들어 **현재 결정, 남은 문제, 상세 기록 링크**를 한눈에 볼 수 있게 한다. 상세 기록은 아트·애니메이션, 조작·게임 로직, 성능·검증처럼 주제별로 나누고, 날짜와 버전이 있는 과거 기록은 상세 문서에 보관한다. 나눈 뒤에는 README 또는 원래 문서에서 요약과 상세 기록으로 바로 이동할 수 있게 한다.
