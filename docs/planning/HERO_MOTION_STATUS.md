## 3. 총이 주무기일 때 별도로 챙길 것

사용자는 총을 메인으로 하겠다고 명확히 말했다. 아래의 ‘추천’은 제작 우선순위이며 구체적인 총 종류/탄창/재장전 규칙을 확정한 것은 아니다. **현재 코드 기본 무기는 아직 machete이고 새 시험도 검만 사용하므로 총 중심 전환이 완료된 상태가 아니다.**

| 항목 | 기존 게임 코드/그림 | 새 주인공 상태 | 구분 / 권장 우선순위 |

P0는 총 중심 기본 조작을 읽을 수 있게 하는 것, P1은 기존 플레이 상태의 시각 누락을 복구하는 것이다. 피격/사망/회피/줍기/살금걷기는 기존 상태가 존재하므로 총 그림을 만들다가 빠뜨리지 않도록 표에 유지한다. 밀치기·밟기는 기본 비활성 기능으로 별도 보류한다.

## 4. 근거와 확인 범위

- 상태별 요청: `src/hero.py`의 `draw`, `start_ready/start_slash/start_roll/take_blow`.
- 파일 선택/대체: `src/character_look.py`의 `DirLook.has/picture/key_pose/has_dir`, `src/dodge_fx.py`의 `rolls`. 파일 이름이 walk이면 일반 walk로 읽는 규칙도 반영했다.
- 현재 실행 연결: `src/play.py`의 기본 HERO_PX와 `tools/run_redjacket_trial.py`의 ART/frame_for/has_dir/draw/reset. 최신 양손 미리보기 폴더가 실제 ART가 아님을 확인했다.
- 총 기능/스위치: `src/weapons.py`, `src/play.py`, `src/settings.py`. R은 현재 재시작 키이며 재장전 완료로 세지 않는다.
- [파일/선택 근거 JSON](HERO_MOTION_INVENTORY.json): 기존 3D 키 참조 168개, PixelLab 10개에서 해당 파일 누락 0. 이것은 품질/가림/발 접지 합격이 아니다.
- 숨김 pico2d 창에서 실제 로더로 17개 요청 × 8방향 × 이전 2종의 선택/대체를 조사하고 새 adapter의 자세 선택 함수를 대조했다. 직접 요청 probe에는 실제 Hero 분기에서 선택되지 않는 요청도 있으므로 위 표는 Hero.has/기능 스위치까지 함께 읽어 작성했다.
- 새 adapter의 roll/roll_spin 요청 자체는 idle을 반환하지만 **실제 Hero는 has_dir=False라 run+잔상으로 회피를 그린다**. 직접 함수 결과만으로 플레이 상태를 단정하지 않는 예다.
- 이번은 코드/파일/로더 조사다. 모든 방향/동작을 실제 플레이·육안으로 새로 검수한 것은 아니다. 게임 코드/그림은 이번 조사에서 변경하지 않았다.
- 기준은 디스크의 기본 설정과 로더다. 사용자가 열어둔 창의 F4 선택값까지 조사한 것은 아니다.

## 5. 앞으로 갱신하는 법

1. 작업 전 해당 행의 기존 상태와 목표를 정한다. 새 동작/그림만 있음/임시 대체/게임 연결/게임 검수를 구분한다.
2. 생성 결과와 손·무기 기준/방향/프레임/타이밍을 기록한다. 발 bbox 정렬만으로 접지 완료 처리하지 않는다.
3. 게임의 해당 상태에 실제 진입해 검수하고, 대기→조준→이동 조준→발사→회복과 피격/회피 중단도 확인한다.
4. 현재 실행 파일이 실제로 새 폴더를 로드하는지 확인한 뒤 이 표와 인수인계를 갱신한다.
5. 파일 근거 갱신: 프로젝트 루트에서 `.venv\Scripts\python.exe tools\checks\audit_hero_motions.py --runtime`. 표의 판단은 코드/플레이 확인 후 사람이 갱신한다. 자동 JSON이 완성 판정을 대신하지 않는다.
